A workbench object whose monomers are GENERATED by a program instead of listed by hand. The recipe stores the program's `source` as a param (beside `params`, `seed`, `budgetMs`) in an ordinary `kind: 'workbench'` manifest; every render runs it (memoised) and lowers what it returns through the same kernel a hand-written spec uses — every validator, group tag, closure audit, ledger line, skin seam, assembler part slot and engine leg is inherited unchanged. Astra's throwaway `bpy` script becomes a stored, seeded, re-runnable, in-place-editable generator of recipes.

## Spec shape

```
{ source, params?, seed?, budgetMs?, units?, viewBox?, facing?, title? }
```

- `source` (required, ≤ 64 KB) — plain JavaScript, the BODY of `function (params, ctx) { … }`. It must `return` synchronously (no Promises) either
  - a **workbench spec** — an object with monomer arrays and/or an `assembly`: `{ lathes?, extrudes?, sweeps?, lofts?, fields?, drapes?, reliefs?, shells?, assembly? }` (the workbench card documents each), lowered exactly as if you had written it; or
  - a **face list** — an array of `{ corners: [[x,y,z], …] (≥ 3), fill?: '#hex', tint?: '#hex', group?: string }`. Faces without `fill` are shaded by their outward normal under the studio light. The closure audit reports what it finds (advisory: an open sheet may be what you meant).
  The return shape is detected, not declared. Explicit monomer arrays passed beside `source` are merged AFTER the program's. Monomer endpoints follow the workbench card exactly: `lathes` / `extrudes` take `axisFrom` / `axisTo` as `{ x, y, z }` objects; `sweeps` / `lofts` paths and every `fields` point take `[x, y, z]` too.
- `params` (object, JSON only) — the dial surface. `update_sketch` changes a number and the program re-runs; changing `source` is the same call. A recipe is a starter, not a one-shot.
- `seed` (number, default 0) — inside the realm `Math.random()` IS `mulberry32(seed)`. Dice are not forbidden; they are seeded. Same program + params + seed → the same object forever.
- `budgetMs` (default 5000, max 60000) — the one limit: wall-clock for the run, the returned value's serialisation included. A `while (true)` fails the mint naming `budgetMs`.
- `units` / `viewBox` / `facing` / `title` — as on the workbench card.

## The realm

The program has the language and nothing of the host. There is no `process`, `require`, `fetch`, `fs`, no timers, no `import()` (refused by the runtime). `Date` throws ("the realm has no clock — a recipe is the same object tomorrow"); `Intl` is absent. `console.log` / `info` / `warn` / `error` are CAPTURED, not printed: the lines come back as `stats.program.log` on the mint result and on a mint ERROR (up to 200 lines / 64 KB), so the loop is mint → read the log or the error → `update_sketch`. A program that throws fails the mint with its message and its log; a program that returns nonsense renders nonsense and meets the eyes gate. Both are the loop working. This fence is for DETERMINISM, not security — the operator's own agent wrote the code on the operator's own machine.

`ctx` is the frozen, versioned, append-only toolkit (`ctx.version >= 2` to feature-check). `ctx.solids`:

- `terms` — every field-terms constructor as `{ d, bounds }` terms: `sphere box capsule ellipsoid roundCone lathe extrude sweep expr`, the combinators `union intersect subtract smoothUnion smoothIntersect smoothSubtract shell round stroke displace`, the domain ops `transform repeat twist bend taper elongate` (each `(solid, spec) → solid`), `fromSpec(shape)`, `SHAPE_KINDS`, `OPS`.
- `compose(terms)` — a recipe-shaped term list → `{ d, bounds, parts }`; `validateTerms(terms)`; `expr.parse(src)` / `expr.compile(ast, vars)`.
- `surfaceNet(d, bounds, { cells })` — polygonize ANY `(p) => number` to closed quads (`{ corners:[{x,y,z}…], n }`); `fieldFaces(spec)` — a whole `fields` monomer as baked faces; `fieldGrid(spec)`.
- `noise3(p, { seed, scale?, octaves?, persistence? })`, `noise3Amplitude`, `mulberry32(seed)`, `transportFrames(points)`, `vec`, `padBounds`, `unionBounds`.

Prefer RETURNING A SPEC: it is smaller, it stays legible in `diff_sketches`, and the kernel does the polygonizing with every gate attached. Return faces only when the geometry is genuinely yours (a computed surface the monomers cannot say).

## Worked program — a bolt-circle flange (spec return, mm)

```
mint_solid({ kind: 'code', title: 'bolt-circle flange', spec: {
  units: 'mm',
  params: { n: 6, r: 40, pcd: 30, hole: 3, t: 6 },
  seed: 7,
  source: `
    const bores = Array.from({ length: params.n }, (_, i) => {
      const a = (i / params.n) * Math.PI * 2;
      const cx = params.pcd * Math.cos(a), cy = params.pcd * Math.sin(a);
      return { id: 'bore', op: 'subtract',
               shape: { kind: 'capsule', a: [cx, cy, -1], b: [cx, cy, params.t + 1], radius: params.hole } };
    });
    console.log('bores', bores.length);
    return { fields: [{ cells: 96, terms: [
      { id: 'disc', op: 'add', shape: { kind: 'lathe', profile: [{ t: 0, radius: params.r }, { t: 1, radius: params.r }], axisFrom: [0, 0, 0], axisTo: [0, 0, params.t] } },
      ...bores,
    ] }] };
  `,
}})
```

`update_sketch` with `params.n = 8` re-runs the loop; the ledger at export carries `code: { source_hash, realm_version, budget_ms, returned: 'spec', monomers }`. (The same flange without a program is one `repeat { polar }` term on the workbench card — reach for the program when the loop is the least of it.)

## Worked program — a parametric staircase (monomers in a loop)

```
spec: {
  units: 'cm',
  params: { steps: 12, rise: 17, run: 28, width: 90, thickness: 4, stringer: 6 },
  source: `
    const { steps, rise, run, width, thickness, stringer } = params;
    const treads = Array.from({ length: steps }, (_, i) => ({
      profile: { rect: { w: run, h: width } },
      axisFrom: { x: i * run + run / 2, y: 0, z: (i + 1) * rise - thickness }, axisTo: { x: i * run + run / 2, y: 0, z: (i + 1) * rise },
      material: 'wood',
    }));
    const stringers = [-width / 2 + stringer / 2, width / 2 - stringer / 2].map((y) => ({
      profile: { points: [[0, 0], [steps * run, (steps - 1) * rise], [steps * run, steps * rise], [0, rise]] },
      axisFrom: { x: 0, y: y - stringer / 2, z: 0 }, axisTo: { x: 0, y: y + stringer / 2, z: 0 },
      material: 'wood',
    }));
    return { extrudes: [...treads, ...stringers] };
  `,
}
```

## Worked program — a train of parts from a parts table (an assembly)

```
spec: {
  units: 'cm',
  params: { cars: [{ len: 60, h: 24, r: 5 }, { len: 40, h: 18, r: 5 }, { len: 40, h: 18, r: 5 }], gap: 6, wheels: 3 },
  seed: 3,
  source: `
    const out = { extrudes: [], lathes: [] };
    let x = 0;
    params.cars.forEach((car, ci) => {
      out.extrudes.push({ profile: { rect: { w: car.len, h: 20 } }, axisFrom: { x: x + car.len / 2, y: 0, z: car.r + 2 }, axisTo: { x: x + car.len / 2, y: 0, z: car.r + 2 + car.h }, tint: ci === 0 ? '#8a2f2f' : '#3f5f8a' });
      for (let w = 0; w < params.wheels; w += 1) {
        const wx = x + (w + 0.5) * (car.len / params.wheels);
        for (const y of [-11, 11]) out.lathes.push({ axisFrom: { x: wx, y: y - 1.5, z: car.r }, axisTo: { x: wx, y: y + 1.5, z: car.r }, profile: [{ t: 0, radius: car.r }, { t: 1, radius: car.r }], material: 'steel' });
      }
      x += car.len + params.gap;
    });
    console.log('parts', out.extrudes.length + out.lathes.length, 'length', x);
    return out;
  `,
}
```

Three cars, eighteen wheels, one recipe; `params.cars` is the parts table. Every part is named in the export ledger and travels to every engine leg like a hand-placed one.

## What this does not change

The seam stays where it was: no mesh CSG, no B-rep, no host scripting, no live DCC driving — a program composes mojulo's own vocabulary and nothing else. The eyes gate stays human. Absent a `program`, every existing workbench re-renders byte-for-byte.
